# Benchmark Acceptance Notes

This note defines how benchmark artifacts should be interpreted before accepting query-performance changes.

The current benchmark target is the small clustered 2D workload. The most useful performance signal is the KD-tree low-selectivity gap because it is the closest tree-baseline comparison.

The current boundary diagnostic target is:

```text
cluster_boundary_range
```

## Required checks before accepting a performance commit

Run the normal Rust checks:

```powershell
cargo fmt
cargo test
cargo check --release
```

Then run the low-gap review workflow.

## Preferred performance-review command

For query-performance commits, prefer the single review runner:

```powershell
.\scripts\run-low-gap-review.ps1 `
  -Label "<commit-label>" `
  -PreviousLabel "<previous-label>" `
  -Trials 5 `
  -Iterations 10000
```

This command runs:

```text
normal benchmark artifact bundle
repeated low-gap trials
target workload repeated-trial summary
target workload repeated-trial comparison
aggregate repeated-trial comparison
weakest-workload repeated-trial comparison
review notes
review artifact manifest
```

The review notes are written to:

```text
benchmark_artifacts/low-gap-review-notes-<commit-label>.txt
```

The review artifact manifest is written to:

```text
benchmark_artifacts/low-gap-review-manifest-<commit-label>.txt
```

Use the review note first to confirm which comparisons completed and which previous inputs were missing.

Use the manifest second to confirm which expected artifacts were produced, skipped, or missing.

## Review artifact manifest workflow

The review artifact manifest is a checklist file generated by:

```text
scripts/run-low-gap-review.ps1
```

The manifest is named:

```text
low-gap-review-manifest-<commit-label>.txt
```

It lists each expected review artifact using this format:

```text
state | artifact | path | note
```

The possible states are:

```text
found
missing
skipped
```

Interpret them as follows:

```text
found: the artifact exists after the review run
missing: the artifact was expected but was not found
skipped: the artifact was intentionally not generated because an input or flag made that step unavailable
```

A manifest with skipped comparison artifacts can still be acceptable when the notes explain that the previous comparison input was unavailable.

A manifest with missing core artifacts is not acceptable for a completed review run.

Core artifacts that should normally be found are:

```text
benchmark output
debug output
summary CSV
workloads CSV
low-selectivity gap CSV
low-gap regression notes
low-gap trial details
low-gap trial summary
low-gap trial notes
low-gap workload trial details
low-gap workload trial summary
target workload trial details
target workload trial summary
target workload trial notes
low-gap review notes
low-gap review manifest
```

Comparison artifacts may be skipped when previous inputs are unavailable:

```text
aggregate trial comparison CSV
aggregate trial comparison notes
workload trial comparison CSV
workload trial comparison notes
target workload trial comparison CSV
target workload trial comparison notes
```

For normal query-performance review, prefer a manifest where all comparison artifacts are found.

For reporting-only commits, it is acceptable for comparison artifacts to be skipped if the skipped reason is clear and the new reporting artifact is found.

## Target workload review options

The review runner targets this workload by default:

```text
cluster_boundary_range
```

To target a different workload:

```powershell
.\scripts\run-low-gap-review.ps1 `
  -Label "<commit-label>" `
  -PreviousLabel "<previous-label>" `
  -Trials 5 `
  -Iterations 10000 `
  -TargetWorkloadName "<workload-name>"
```

To explicitly provide a previous target workload summary:

```powershell
.\scripts\run-low-gap-review.ps1 `
  -Label "<commit-label>" `
  -PreviousLabel "<previous-label>" `
  -Trials 5 `
  -Iterations 10000 `
  -PreviousTargetSummaryCsv "benchmark_artifacts\target-workload-trial-summary-<previous-label>.csv"
```

To skip target workload review for a non-performance or workflow-only run:

```powershell
.\scripts\run-low-gap-review.ps1 `
  -Label "<commit-label>" `
  -PreviousLabel "<previous-label>" `
  -Trials 5 `
  -Iterations 10000 `
  -SkipTargetWorkloadReview
```

Do not skip target workload review for boundary-focused performance commits.

## Review note interpretation

Use this file first:

```text
low-gap-review-notes-<commit-label>.txt
```

It should clearly report previous input availability:

```text
single-run low-selectivity CSV status
aggregate trial summary status
workload trial summary status
target workload trial summary status
```

It should also clearly report comparison availability:

```text
single-run low-gap comparison
aggregate repeated-trial comparison
workload repeated-trial comparison
target workload summary
target workload comparison
```

A missing previous single-run low-selectivity CSV is not fatal when the repeated-trial summaries are available. The repeated-trial comparisons are stronger than the single-run low-gap regression notes.

A missing previous aggregate or workload summary is not fatal for a reporting-only commit when the review notes and manifest clearly mark those comparisons as skipped.

A missing previous target workload summary is not acceptable for a boundary-focused performance commit unless this is the first commit that generated the target workload summary path.

## Primary aggregate acceptance signal

Use:

```text
low-gap-trial-summary-<commit-label>.csv
```

The primary field is:

```text
kd_tree.mean_low_mean_timing_ratio
```

The comparison field is:

```text
kd_tree.delta_from_previous
```

The default noise threshold is:

```text
+/- 0.030000
```

A positive delta means FSE improved relative to KD-tree because the timing ratio is:

```text
baseline elapsed / FSE elapsed
```

Higher is better for FSE.

A boundary-focused performance commit should improve the repeated-trial target workload mean, not just one single debug run.

The weakest-workload summary is used to confirm what workload is losing most often. It should not replace the target-workload comparison when a specific workload was intentionally optimized.

If a previous workload-trial summary exists, compare:

```text

```

```text
+0.030000
```

The boundary workload summary is also used to confirm that the same workload is actually being targeted. If `cluster_boundary_range` is not the most frequent weakest KD-tree workload, do not assume a boundary optimization was tested cleanly.

## Accept rule

Accept a query-performance commit when all of these are true:

```text
cargo test passes
cargo check --release passes
matched record counts remain exact
validation remains pass
candidate counts are unchanged unless the commit intentionally changes pruning
flat_scan and r_tree do not show broad weighted-timing regressions
review manifest has no missing core artifacts
```

Then require at least one of these aggregate performance signals:

```text
kd_tree.mean_low_mean_timing_delta >= +0.030000
kd_tree.timing_classification == improved
```

or, for a boundary-focused optimization, require this target workload comparison signal:

```text
kd_tree.current_workload_name == cluster_boundary_range
kd_tree.timing_classification == improved
kd_tree.mean_timing_delta >= +0.030000
kd_tree.mean_fse_visited_nodes_delta <= 0 unless intentionally changed
kd_tree.mean_fse_reconstructed_records_delta <= 0 unless intentionally changed
kd_tree.mean_candidate_ratio_delta <= 0 unless intentionally changed
kd_tree.mean_fse_matched_records_delta == 0
kd_tree.mean_baseline_matched_records_delta == 0
```

or, when the target workload is still also the weakest workload, require this weakest-workload comparison signal:

```text
kd_tree.current_weakest_workload == cluster_boundary_range
kd_tree.timing_classification == improved
kd_tree.mean_weakest_timing_delta >= +0.030000
kd_tree.mean_fse_visited_nodes_delta <= 0 unless intentionally changed
kd_tree.mean_fse_reconstructed_records_delta <= 0 unless intentionally changed
kd_tree.mean_candidate_ratio_delta <= 0 unless intentionally changed
```

A performance commit should also preserve the expected structural invariants unless the commit intentionally changes traversal or index construction:

```text
same dataset record count
same workload count
same selected baselines
same validation status
same exact result correctness
```

## Rerun rule

Rerun the benchmark before deciding when any of these are true:

```text
kd_tree.classification == stable/noise
abs(kd_tree.delta_from_previous) < 0.030000
kd_tree.timing_classification == stable/noise
abs(kd_tree.mean_low_mean_timing_delta) < 0.030000
abs(kd_tree.mean_weakest_timing_delta) < 0.030000
abs(kd_tree.mean_timing_delta) < 0.030000
kd_tree.range_low_mean_timing_ratio is larger than 0.030000
kd_tree.range_weakest_timing_ratio is larger than 0.030000
kd_tree.range_timing_ratio is larger than 0.030000
target workload sample stddev is close to the apparent improvement
debug output and CSV output disagree on the weakest workload
target workload comparison and workload comparison disagree
one trial is much better or worse than the others
cluster_boundary_range is not consistently the weakest KD-tree workload
aggregate trial comparison and workload trial comparison disagree
review manifest says a core artifact is missing
review notes and review manifest disagree
```

A single good benchmark run is not enough to keep a query-performance commit if the repeated-trial mean stays inside the noise band.

A single good boundary workload row is also not enough. Use the target workload comparison, workload trial summary, and workload comparison artifact before deciding.

## Revert rule

Revert a query-performance commit when any of these are true:

```text
cargo test fails
cargo check --release fails
matched record counts change
validation fails
candidate counts change unexpectedly
kd_tree.mean_low_mean_timing_delta <= -0.030000
kd_tree.timing_classification == regressed
kd_tree.mean_weakest_timing_delta <= -0.030000
kd_tree.mean_timing_delta <= -0.030000 for the target workload
the code becomes more specialized without a repeated-trial win
review manifest shows missing core artifacts after a completed review run
```

If a commit only changes report formatting, artifact generation, or notes, do not revert it based on timing movement alone. Reporting-only commits should be judged by artifact correctness.

```powershell
  -Label "<commit-label>" `
  -PreviousTrialSummaryCsv "benchmark_artifacts\low-gap-trial-summary-<previous-label>.csv" `
  -CurrentTrialSummaryCsv "benchmark_artifacts\low-gap-trial-summary-<commit-label>.csv"
```

Expected outputs:

```text
low-gap-trial-comparison-<commit-label>.csv
low-gap-trial-comparison-<commit-label>.txt
```

Use the comparison notes to check:

```text
previous mean low timing
current mean low timing
mean low timing delta
classification
range delta
sample stddev delta
mean weighted candidate delta
mean weighted avoidance delta
```

For an aggregate low-selectivity optimization, a clean positive result should look like this:

```text
mean low timing delta: greater than +0.030000
classification: improved
mean weighted candidate delta: 0.000000 or lower unless intentionally changed
mean weighted avoidance delta: 0.000000 or higher unless intentionally changed
range delta: not large enough to explain the improvement as noise
sample stddev delta: not large enough to explain the improvement as noise
```

A noisy result looks like this:

```text
classification: stable/noise
mean low timing delta: between -0.030000 and +0.030000
```

A weak or suspicious result looks like this:

```text
timing improved but candidate ratio increased
timing improved but avoidance ratio decreased
timing improved but range or sample stddev grew sharply
```

## Interpreting low-gap trial notes

Use this file:

```text
low-gap-trial-notes-<commit-label>.txt
```

A useful aggregate performance win should look like this:

```text
kd_tree
-------
classification: improved
delta from previous: greater than +0.030000
range: not much larger than the improvement
mean weighted candidate: unchanged unless intended
mean weighted avoidance: unchanged unless intended
```

A useful boundary workload win should look like this:

```text
kd_tree
-------
target workload: cluster_boundary_range
mean target timing: improved by more than +0.030000 against the previous target-workload summary
mean FSE visited nodes: unchanged or lower
mean FSE reconstructed records: unchanged or lower
mean baseline evaluated records: unchanged
mean candidate ratio: unchanged or lower
```

A useful weakest-workload win should look like this:

```text
kd_tree
-------
most frequent weakest workload: cluster_boundary_range
mean weakest timing: improved by more than +0.030000 against the previous workload-trial summary
mean FSE visited nodes: unchanged or lower
mean FSE reconstructed records: unchanged or lower
mean baseline evaluated records: unchanged
mean candidate ratio: unchanged or lower
```

A noisy result looks like this:

```text
classification: stable/noise
delta from previous: between -0.030000 and +0.030000
range or sample stddev is close to the size of the apparent improvement
```

A regression looks like this:

```text
classification: regressed
delta from previous: less than -0.030000
boundary workload mean timing regressed by more than -0.030000
```

## Decision order

Use this order when reviewing benchmark artifacts:

```text
1. cargo test and cargo check result
2. low-gap review notes
3. low-gap review manifest
4. normal compact benchmark summary
5. target workload trial summary CSV and notes
6. target workload comparison CSV and notes
7. low-gap trial summary CSV
8. low-gap trial comparison CSV and notes
9. low-gap workload trial summary CSV
10. low-gap workload comparison CSV and notes
11. low-gap trial notes
12. workload CSV
13. debug report
14. single-run low-gap regression notes
```

The single-run low-gap regression notes are useful, but they are not the final decision source for performance commits. The repeated-trial summary and comparator outputs are stronger.

For boundary-focused commits, the target workload summary and target workload comparison artifact are required because the aggregate low-selectivity bucket can hide whether `cluster_boundary_range` actually improved.

The workload trial summary and workload comparison artifact are still required to confirm whether `cluster_boundary_range` remains the weakest workload.
